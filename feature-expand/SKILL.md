# feature-expand：把一句话需求展开成能用的功能

用户说「实现一下下拉框」时，他要的是一个能用的选择器，不是一个 `<select>` 标签。
搜不搜索看决策表，不是默认都做搜索。
本 Skill 的用法：**识别类型 → 只读对应剧本 → 填默认值 → 按 done.md 验收**。
禁止自己发明流程。禁止跳过下面任何一步。

## 执行步骤（按顺序做，每一步都是命令）

1. **识别表面类型**。对照下面的路由表，把用户的话归到一个类型。
2. **只读对应的那一份 reference**。禁止一次读完所有 reference。
3. **套剧本，先贴决策表再写代码**。按剧本里的默认决策表逐行填值。
   写任何文件之前，必须先在回复里贴一张已填的决策表，至少包含：
   类型、单选或多选（或本类型对应的关键维度）、数据来源、搜索策略、
   分页/虚拟列表策略、必须实现的状态。
   没贴这张表，禁止创建或修改代码文件。
   模板（必须原样抄出来再填空，禁止只描述字段名）：

   ```text
   类型：
   单选/多选（或本类型关键维度）：
   数据来源：
   搜索策略：
   分页/虚拟列表：
   必须实现的状态：
   走的是：默认路径 / 最小路径
   ```

   没填满这一张，禁止改代码。
   状态和可用性按表补：空、加载、失败、禁用，用户没提也要做。
   表里没有的功能（收藏、导出、筛选器、历史记录）禁止加。
4. **最多问 1–2 个会改架构的问题**（例如：接口是全量返回还是分页）。
   其余一律用默认值，禁止问「要不要做搜索」「要不要分页」这类剧本已给默认的问题。
   禁止把「要不要把选项写死在组件里」当成可选项——选项必须来自 props 或接口。
5. **用项目现有技术栈和现有组件实现**。先搜代码库里有没有 Select/Table/Form/Modal 组件。
   有就复用。禁止另起一套 UI 库，禁止绕过项目已有组件自己手写一个。
6. **写完代码后，先读 `references/traps.md` 对号入座，改掉命中的坑；
   再读 `references/done.md` 逐条自检**。缺一个状态就补一个。
   两条都过了才能说完成。不许在缺态的情况下声称完成。
7. **用户明确说「只要最小实现 / 先出个 demo / 不要多余功能 / 先能提交就行」时，走剧本里的最小路径**。
   最小路径仍然必须覆盖空态、加载态、失败态、禁用态；选择器还必须已选回显；
   表单还必须失败保留数据和提交中禁用按钮。禁止裸 happy path。

## 类型路由表

| 用户话里出现 | 类型 | 必须读 |
| --- | --- | --- |
| 下拉、下拉框、select、选择、选项、多选、级联 | 选择器 | `references/select.md` |
| 表格、列表、展示数据、table、list | 表格列表 | `references/table.md` |
| 表单、提交、填写、新增、编辑、form、上传 | 表单 | `references/form.md` |
| 弹窗、弹层、抽屉、对话框、确认框、modal、drawer | 弹层 | `references/overlay.md` |
| 以上都不匹配 | 其他 | 只读 `references/traps.md` 和 `references/done.md` |

类型以主体功能为准，修饰词（分页、搜索、多选）不单独改变类型。
用户说「下拉框要分页」→ 只读 `references/select.md`，禁止再读 `references/table.md`。
只有话里出现「表格 / 列表 / table / list / 展示数据」才读 `references/table.md`。
一个需求命中多个类型时（如「弹窗里有个表单」），每命中一个类型就读对应那份，仍禁止预读没命中的。

## 硬规则（违反任何一条 = 没完成任务）

- **必须**展开隐式需求：空态、加载态、失败可重试、禁用态。用户没提不等于不要。
- **默认**用剧本给的值，**禁止**把决策抛回给用户。能默认的一律默认。
- **禁止**只做字面功能。「实现下拉框」≠ 渲染一个 `<select>`。
- **禁止**过度设计。用户要一个选择器，不要造完整的中台筛选系统。剧本表里没有的功能不做。
- **禁止**无视项目已有组件另写一套。
- **禁止**先列 8 个问题等用户批准再动手。最多 1–2 个改架构的问题，其余直接按默认做。

## 锚点例子 A：「实现一下下拉框」

- **用户原话**：实现一下下拉框。
- **弱模型错误产出**：原生 `<select>` + 写死选项 + 只有 happy path（没有空/加载/失败态）+ 数据一大就卡。
  没做搜索本身不是错：只有「数量未知却完全没过滤」或「>20 还没过滤」才是错。
- **正确做法**：识别为「选择器」，读 `references/select.md`，按默认决策表实现，
  而不是只做字面功能。
- **默认决策表**：

| 维度 | 默认 | 升级条件 |
| --- | --- | --- |
| 单选/多选 | 单选 | 用户明确说可多选才做多选 |
| 数据来源 | 选项必须来自 props 或接口，禁止在组件里写死业务选项；来源不明时先做成 props 传入，再最多问 1 句「接口是全量返回还是分页？」 | 用户指明接口则走接口 |
| 搜索 | 已确认固定 ≤20 → 不做搜索；数据来源或数量未知 → 先按会超过 20 项处理，做本地过滤；全量 51–200 → 全量渲染 + 本地过滤 | 接口分页或数据会随业务增长 → 服务端搜索 + 防抖 300ms + 竞态保护 |
| 分页/虚拟列表 | 全量 ≤50 → 全量渲染；全量 51–200 → 全量渲染 + 本地过滤 | 全量 >200 或接口分页或数据会随业务增长 → 虚拟列表或接口分页；接口本身分页则跟接口 |
| 状态 | 空、加载、失败可重试、禁用必做；无匹配仅做了搜索时必做 | 无升级项，这是底线 |
| 已选回显 | 关面板后仍能看到当前值；多选显示数量或标签 | 无升级项，这是底线 |
| 键盘 | 默认路径必须做：打开、上下移动、回车选中、Esc 关闭、输入即过滤 | 用户明确说「只要最小实现 / 先出个 demo / 不要多余功能」时可砍，不是所有任务都是底线 |
| 性能 | 禁止一次把 1000 个 option 塞进 DOM | 无升级项，这是禁令 |

- **禁止**：用原生 `<select>` 硬撑大数据；只做 happy path；不留数据入口、在组件里写死 5 个 option。
- **该问什么**：只问会改架构的问题（最多 1–2 个），例如「接口是全量返回还是分页？」。
- **不该问什么**：「要不要搜索？」「要不要空态？」——表里已有默认，直接做。

## 锚点例子 B：「做个表格」

- **用户原话**：做个表格 / 把列表展示出来。
- **弱模型错误产出**：一个写死表头的 `<table>`，把接口返回的数组直接 map 出来，
  没有空数据提示、没有加载骨架、没有失败重试；「分页」是把数组 slice 前 10 条假装翻页。
- **正确做法**：识别为「表格列表」，读 `references/table.md`，按默认决策表实现。
- **默认决策表**：

| 维度 | 默认 | 升级条件 |
| --- | --- | --- |
| 数据来源 | 来源不明时先按接口分页写（传 page/pageSize），同时最多问 1 句「接口是分页返回还是一次全返？」；禁止不问也不写分页参数、把全量数据拉到前端、把行数据写死在组件里 | 用户或接口文档确认一次全返且 ≤100 条 → 才改前端分页 |
| 分页 | 接口分页 → 传 page/pageSize，翻页重新请求；一次全返且 ≤100 条 → 前端分页（最小路径可砍分页，砍了就一次渲染完，仍禁止 slice 假装分页） | 一次全返且 >1000 条 → 先要求接口分页，做不到再虚拟滚动 |
| 状态 | 必须有：空数据、加载骨架（或 loading 行）、失败可重试 | 无升级项，这是底线 |
| 列对齐 | 文本左对齐、数字右对齐、操作列固定在最右 | 无升级项，这是底线 |
| 排序/筛选 | 不做 | 用户明确要求才做 |
| 空值单元格 | 显示「-」，禁止显示 undefined/null | 无升级项，这是底线 |
| 操作列 | 用户提到编辑/删除才加；删除必须走确认弹层 | 无升级项 |

- **禁止**：slice 前 10 条假装分页；无视接口分页参数把全量数据拉到前端。
- **该问什么**：「接口是分页返回还是一次全返？」（会改架构，值得问）。
- **不该问什么**：「要不要空态？」「要不要加载中？」——直接做。

## 锚点例子 C：「加个提交」

- **用户原话**：做个表单 / 加个提交。
- **弱模型错误产出**：几个 input 加一个提交按钮；点提交直接发请求；
  提交中按钮还能连点；失败后表单被清空、只 toast 一句「失败」；没有任何校验。
- **正确做法**：识别为「表单」，读 `references/form.md`，按默认决策表实现。
- **默认决策表**：

| 维度 | 默认 | 升级条件 |
| --- | --- | --- |
| 校验时机 | 默认路径必须做：失焦校验单字段 + 提交校验全部并聚焦第一个错误 | 用户明确说「只要最小实现 / 先出个 demo / 不要多余功能 / 先能提交就行」时可砍失焦，但提交时全量校验、字段旁错误、聚焦第一个错误仍必须。不是所有任务都把失焦当底线 |
| 错误展示 | 错误信息显示在对应字段旁边，写清哪里错、怎么改 | 无升级项。禁止只 toast「失败」 |
| 提交中 | 按钮禁用 + loading，防止重复提交 | 无升级项，这是底线 |
| 失败后 | 保留用户已填数据，展示可读的错误原因，可以重试 | 无升级项。禁止清空表单 |
| 成功后 | 给出成功反馈；新增场景重置表单，编辑场景保留并提示已保存 | 用户指定跳转则跳转 |
| 必填标记 | 必填字段有标记；未填完时提交按钮可点但提交时报错定位 | 无升级项 |
| 编辑回填 | 仅编辑场景必须：先拉详情回填，回填前显示加载态；新增/纯提交场景不做回填 | 无升级项。禁止凭空做一套编辑流程 |

- **禁止**：提交按钮不禁用；失败清数据；错误只有一句「失败」。
- **该问什么**：「提交到哪个接口？字段有没有后端校验规则？」（会改架构，值得问）。
- **不该问什么**：「要不要 loading？」「失败要不要保留数据？」——直接做。

## 验收门（提交前的最后一道，禁止跳过）

写完代码后，回答下面四个问题。任何一个答「否」，就回去补，补完再来。

1. 数据为空时，界面有可读的空态提示吗？
2. 请求进行中，用户能看到加载反馈、且不能重复触发吗？
3. 请求失败时，用户能看到原因并且能重试吗？数据丢了吗？
4. `references/done.md` 里对应类型的清单，每一条都过了吗？

四个都「是」，才可以说「完成」。
